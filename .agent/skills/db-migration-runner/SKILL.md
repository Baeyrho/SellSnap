# SKILL — DB Migration Runner

> Use this skill before adding, editing, or removing anything in the Prisma schema. It covers the schema conventions this project actually uses, the migration workflow, seeding, and production deployment.

---

## Before You Start

1. Read `.agent/rules/architecture.md` — data access rules, Prisma singleton pattern.
2. Read `.agent/rules/code-style.md` — TypeScript rules, kobo currency convention.
3. Read `.agent/rules/security.md` — password hashing and PII handling, relevant when adding user-facing fields.

## Rules

- All database access in application code goes through **Prisma Client** — no exceptions.
- Raw SQL is only permitted inside Prisma-generated migration files in `prisma/migrations/`.
- `$queryRaw` in application code requires a comment explaining why Prisma's relational API cannot be used, plus a code review.
- `prisma/schema.prisma` is the single source of truth for the data model.
- Prisma Client is always imported from `lib/prisma.ts`. Never instantiate `new PrismaClient()` elsewhere.

---

## Layout

```
prisma/
├── schema.prisma       ← edit here only
├── seed.ts             ← dev seed; run outside the Next.js build, so use relative imports
└── migrations/         ← generated by `prisma migrate dev`
```

`prisma.config.ts` at the repo root holds the Prisma 7 configuration — the schema path, migrations path, seed command, and the datasource URL.

## Configuration Lives in `prisma.config.ts`, Not the Schema

This project uses Prisma 7. The datasource block in `schema.prisma` intentionally has **no `url`**:

```prisma
datasource db {
  provider = "postgresql"
}
```

The connection string is supplied by `prisma.config.ts`:

```ts
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
    seed: "tsx prisma/seed.ts",
  },
  datasource: {
    url: env("DATABASE_URL"),
  },
});
```

Consequences:

- **Do not add `url = env("DATABASE_URL")` to `schema.prisma`.** The URL is already configured centrally, and duplicating it reintroduces the Prisma 6 pattern this project has moved off.
- The seed command is declared in `prisma.config.ts` → `migrations.seed`, **not** in a `prisma` key in `package.json`.
- The Prisma CLI loads `.env` (not `.env.local`) through the `dotenv/config` import, so `.env` must contain `DATABASE_URL` for migrations and seeding to work. The running Next.js app reads `.env.local`.

## Schema Conventions Used by This Project

These are the conventions the existing schema follows. Match them.

| Concern | Convention in this project | Example |
|---|---|---|
| Primary keys | `@id @default(uuid())` | `id String @id @default(uuid())` |
| Timestamps | `createdAt @default(now())`, `updatedAt @updatedAt` | see `Product` |
| Soft deletes | `deletedAt DateTime?` | `Product.deletedAt` |
| Currency | `Int` in kobo — never `Float` or `Decimal` | `priceKobo Int` |
| Table names | **Prisma model name as-is** — PascalCase, no `@@map` | table `Product`, column `priceKobo` |
| Column names | **Field name as-is** — camelCase, no `@map` | `sellerId`, `transactionRef` |
| Enums | `UPPER_SNAKE_CASE` values | `ProductStatus.ACTIVE` |
| Relations | `onDelete` stated explicitly on every relation | see below |

Earlier versions of this skill prescribed `cuid()`, `@@map("snake_case_table")`, and `@map("seller_id")`. **None of that is used here.** The existing migrations created PascalCase tables with camelCase columns, and retro-fitting `@map` would generate a destructive table-and-column rename. Do not introduce it.

### Model template

```prisma
model Product {
  id          String         @id @default(uuid())
  sellerId    String
  slug        String         @unique
  name        String
  description String?
  priceKobo   Int
  imageUrl    String
  status      ProductStatus  @default(ACTIVE)
  deletedAt   DateTime?
  createdAt   DateTime       @default(now())
  updatedAt   DateTime       @updatedAt
  seller      User           @relation(fields: [sellerId], references: [id], onDelete: Cascade)
  orders      Order[]

  @@index([sellerId])
  @@index([slug])
  @@index([status])
}
```

Key points:

- `sellerId` is the foreign key field, `seller` is the relation object — both are required.
- `slug` is globally `@unique`, so it is a single seller-agnostic namespace. Do not convert it to `@@unique([sellerId, slug])` without a migration plan and a slug-collision decision.
- `@@index([status])` serves the "only ACTIVE products are payable" filter on the public pay route.
- `@unique` implies an index; a redundant `@@index` on the same column is noise. `User.email` and `Product.slug` both do this — leave them as they are rather than churning the schema.

## Relations and `onDelete`

Every relation declares `onDelete` explicitly. The values in use are not uniform, and the difference is deliberate:

| Relation | `onDelete` | Why |
|---|---|---|
| `Product.seller` | `Cascade` | A seller's products go with the seller |
| `Order.product` | `Restrict` | Financial records must not disappear with a product |
| `Order.seller` | `Restrict` | Same — the seller's order history is an audit trail |
| `PasswordResetToken.user` | `Cascade` | Ephemeral auth artefacts |
| `RetiredEmail.user` | `Cascade` | Tied to the account lifecycle |

Orders are deliberately `Restrict`. Do not "fix" them to `Cascade` — deleting a product or seller must not silently erase the seller's sales records. SellSnap soft-deletes products (`status: 'DELETED'` + `deletedAt`) precisely so this stays true.

## Adding or Changing a Model

### Step 1 — Edit `prisma/schema.prisma`

Follow the conventions above. Read the neighbouring models rather than inventing a new shape.

### Step 2 — Create and apply the migration

```bash
npx prisma migrate dev --name describe_the_change
```

This generates a migration in `prisma/migrations/` and applies it to the development database. `prisma generate` runs automatically afterwards; run it manually only if needed:

```bash
npx prisma generate
```

Name migrations descriptively with underscores. Existing names follow `0_init` then `add_x_to_y`:

```
0_init
20260907090747_add_profile_fields_to_user
20260914000000_add_seller_location_and_phone
20260921132045_add_retired_email
20261003120000_add_refund_state_to_order
20261004120000_add_below_minimum_refund_status
```

Good names: `add_tags_to_product`, `add_password_reset_token_table`, `add_flw_subaccount_id_to_user`, `add_refund_state_to_order`.

### Step 3 — Update shared types

If you added or removed fields used across the application, update `types/index.ts`. Check what is already there before adding a parallel type — `lib/payments.ts` exports `ResolvableOrder` derived from a Prisma payload via `Prisma.OrderGetPayload`, so changing the `Order` include shape may need that regenerated rather than hand-edited.

### Step 4 — Update route validation

Any new user-facing field needs server-side validation in the relevant route handler. See `.agent/skills/api-route-scaffolder/SKILL.md`.

### Step 5 — Update the seed if the model needs dev data

See *Seeding* below.

## Adding a Field to an Existing Table

When the table already has data, a new field must be either optional or carry a default. Otherwise the migration fails.

```prisma
description String?                       // ✅ safe — optional
status      ProductStatus @default(ACTIVE) // ✅ safe — has a default
description String                         // ❌ unsafe on a populated table
```

For a required field without a default, use a two-step migration:

1. Add the field as optional (`String?`), migrate.
2. Backfill existing rows.
3. Change it to required (`String`), migrate again.

Note that several columns on this schema (`businessBio`, `displayName`, `whatsappNumber`, `phoneNumber`, `businessLocation`, `logoUrl`, `bankCode`, `accountNumber`, `flutterwaveSubaccountId`, `refundStatus`, `refundId`) are nullable — that is what made those migrations safe against existing rows.

---

## Removing a Field

Removing a field **permanently deletes the data** in that column.

Before removing:

1. Confirm the field is no longer referenced in any route handler, component, type, or select clause.
2. Back up the data if it matters.
3. Create the migration: `npx prisma migrate dev --name remove_x_from_y`.

Removing a field from the Prisma model does **not** drop the column — the column stays until a hand-written migration drops it. If you actually need the data gone, write that migration explicitly and justify it in a comment.

---

## Modifying Enums

Adding a value is safe. Removing or renaming one is not: existing rows using that value will break the migration.

```prisma
// Before
enum OrderStatus { PENDING  SUCCESS  FAILED }
// After — safe addition
enum OrderStatus { PENDING  SUCCESS  FAILED  CANCELLED }
```

`OrderStatus` is `PENDING | SUCCESS | FAILED` and must stay that way. Refund lifecycle lives in the separate `RefundStatus` enum (`REQUESTED | COMPLETED | FAILED | BELOW_MINIMUM`) precisely so it never had to be added here. Do not add a `REFUNDED` order status.

## Production Migrations

In production (Vercel), apply migrations with:

```bash
npx prisma migrate deploy
```

**Never run `prisma migrate dev` in production.** It can reset data.

The current `build` script is plain `next build` — it does **not** run `prisma migrate deploy`. Migrations must be applied as a separate deploy step. If you add them to the build command, verify the ordering works with the Prisma 7 `prisma.config.ts` setup first; a build-time migrate that cannot reach the database will fail the deployment.

---

## Migration Reset

```bash
# Destroys all data — development only
npx prisma migrate reset
```

Use only when starting fresh in development or recovering from a broken migration state. **Never against production.**

## Seeding

`prisma/seed.ts` seeds development users, products, and orders. It runs outside the Next.js build, so `@/` aliases are unavailable — use relative imports:

```ts
import { prisma } from '../lib/prisma'
```

The seed command is registered in `prisma.config.ts`, so run it with:

```bash
npx prisma db seed
```

`console.error` is acceptable in this dev-only script.

## Checking the Current State

```bash
npx prisma migrate status   # which migrations are applied / pending
npx prisma studio           # browser GUI
npx prisma db pull          # pull the live schema into schema.prisma
```

`db pull` overwrites `schema.prisma`. Only run it deliberately, and review the diff — it will rewrite formatting and can drop the doc comments the enums carry.

## Current Schema Reference

Models → tables (PascalCase, no `@@map`):

| Model | Table | Notes |
|---|---|---|
| `User` | `User` | seller accounts; `email` unique |
| `Product` | `Product` | `slug` unique; `priceKobo`; soft delete |
| `Order` | `Order` | `transactionRef` unique; payment record |
| `PasswordResetToken` | `PasswordResetToken` | `token` unique, hashed digest |
| `RetiredEmail` | `RetiredEmail` | `email` unique; blocks re-registration |

Enums:

```prisma
enum ProductStatus { ACTIVE  INACTIVE  DELETED }
enum OrderStatus   { PENDING  SUCCESS  FAILED }
enum RefundStatus  { REQUESTED  COMPLETED  FAILED  BELOW_MINIMUM }
```

There is **no** `Payment`, `ProductLink`, or `PaymentStatus` model, and no `payments` table. Payment state lives on `Order` (`status`, `flutterwaveTxId`, `amountKobo`) and, for reversals, on `refundStatus` / `refundId`. Earlier versions of this skill listed all three; ignore them.

All monetary fields are `Int` in kobo. All foreign keys have explicit `onDelete` and `@@index`.

## Common Mistakes

| Mistake | Correct approach |
|---|---|
| Adding `url = env("DATABASE_URL")` to `schema.prisma` | It lives in `prisma.config.ts` (Prisma 7) |
| Using `cuid()` for a new primary key | `@default(uuid())`, matching every existing model |
| Adding `@@map("snake_case")` or `@map("snake_case")` | No mapping is used; it would force a destructive rename |
| Referencing `prisma.payment` or a `Payment` model | It does not exist; payment state is on `Order` |
| Adding a `REFUNDED` value to `OrderStatus` | Use `RefundStatus` |
| Setting money as `Float` or `Decimal` | `Int` in kobo |
| Changing `Order` relations from `Restrict` to `Cascade` | Orders are an audit trail; products are soft-deleted instead |
| Instantiating `new PrismaClient()` outside `lib/prisma.ts` | Import from `@/lib/prisma` |
| Writing raw SQL in a route handler | Use Prisma's query API |
| Forgetting `prisma generate` after a schema change | It runs automatically after `migrate dev` |
| Running `prisma migrate dev` in production | `prisma migrate deploy` |
| Naming migrations vaguely (`migration1`, `update`) | `add_x_to_y`, `create_x_table` |
| Adding a required field without a default to a populated table | Make it optional or give it a default |
| Forgetting `@@index` on a foreign key | Index fields used in `where` clauses |
| Omitting `onDelete` | Always set `Cascade`, `Restrict`, or `SetNull` |
| Expecting a removed field to drop the column | The column survives; write an explicit migration |
| Updating only `package.json` for the seed command | It is in `prisma.config.ts` |

## Checklist Before Submitting a Schema Change

- [ ] New models match the template: `uuid()` id, timestamps, indexes
- [ ] No `@@map` / `@map` introduced
- [ ] No `url` added to the datasource block
- [ ] All relations have an explicit `onDelete`, with orders left as `Restrict`
- [ ] Foreign key fields have `@@index`
- [ ] Unique fields have `@unique`
- [ ] New fields on existing tables are optional or have a default
- [ ] Currency fields are `Int` in kobo
- [ ] Enum values are `UPPER_SNAKE_CASE`; `OrderStatus` is unchanged
- [ ] Migration named descriptively (`add_x_to_y`)
- [ ] `prisma generate` has run (or `migrate dev` was used)
- [ ] `types/index.ts` and any `Prisma.*GetPayload` types updated
- [ ] Relevant route validation updated
- [ ] Seed file updated if the model needs dev data
- [ ] `npm run typecheck` and `npm test` pass
